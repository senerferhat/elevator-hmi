## 1. THE BIG THING: the display works. Do not re-open it.

**BLK-014 is RESOLVED.** The LMT101SX006C panel displays correctly: Tux boot
logo + live framebuffer console, confirmed on glass 2026-08-07.

It took ~2 months and it was **never a hardware fault**. Two stacked bugs:

1. **DSI init ordering** (the real bug). This Rockchip vendor kernel switches the
   DSI host to VIDEO mode in `dw_mipi_dsi_bridge_atomic_enable()` **before**
   calling `drm_panel_enable()`. The mainline-style jadard driver sent the whole
   vendor bring-up from `enable()`, i.e. as HS commands inside the blanking of an
   already-running video stream — the panel received video before it was
   initialised. **Fixed by patch `0021-drm-panel-jadard-lmt101-init-in-prepare`**,
   which moves the sequence into `prepare()` (command mode, pre-video).
2. **`CONFIG_FRAMEBUFFER_CONSOLE` was unset**, so `/dev/fb0` existed but nothing
   ever rendered into it. A zero-filled framebuffer is a correctly-displayed
   BLACK screen. This hid fix (1) for two weeks. Now enabled with `CONFIG_LOGO`.

**Formally exonerated — do not re-investigate:** both panel units, the 3.3 V
rail, XRES timing (scope-verified 20 ms), all 4 MIPI lanes + clock, FPC wiring,
the VCC3V3_LCD load switch, the vendor's init file (byte-verified 196/196).

**Red herrings that wasted weeks — ignore them if they reappear:**
- `0x45 scanline = 0x00` — NOT a reliable liveness indicator here.
- `0x0A` bit7 "booster off" — the vendor's own *healthy* fixture reads `0x18`,
  bit7 also clear. It never indicated a fault.
- `0x0F = 0xC0` was the panel correctly reporting itself healthy all along.
- BIST (`E3,01`) **never produces a visible pattern on this panel** under any
  condition tested, and it leaves the panel degraded (`0x0A=0x08`, `0x0F=0x00`)
  that a bare XRES reset does not clear. **BIST is useless here — do not use it
  as a test instrument.**

**Process lesson that caused the 2-week delay:** patch 0021's kill test was
"pattern visible OR 0x45 non-zero", and it was validated **only via BIST** — an
instrument that had never produced a positive result and therefore could not
report a trustworthy negative. Before trusting a negative result, confirm the
instrument can produce a positive one.

## 4. Rules learned the hard way — follow these

- **Never flash from `build/tmp/deploy/`.** Yocto **deletes** the previous
  build's timestamped `.wic` on every new build. Symlinks there go dangling and
  cause failed flashes (this cost two wasted flash attempts). **Hardlink** every
  image worth keeping into `images-archive/` (zero extra disk, survives pruning)
  and flash from there. `images-archive/` is gitignored.
- **Never `git add` `images-archive/`.** The WIC files are ~3 GB each; they were
  once committed by accident and GitHub rejected the push, requiring a
  `filter-branch` history rewrite. They are gitignored — keep it that way.
- **`git push`** works via the deploy-key alias already set as origin:
  `git@github-elevator-hmi:senerferhat/elevator-hmi.git`. The default SSH key is
  NOT authorised for this repo. `backup-pre-filter` branch holds pre-rewrite
  history and can be deleted once you're confident.
- **Do NOT re-enable kernel patches 0022, 0023 or 0024** in
  `meta-hmi-platform/recipes-kernel/linux/linux-rockchip_%.bbappend` for any
  image meant to display. 0021 alone is the proven-working config. 0022/0024 arm
  BIST (leaves the panel degraded); 0023 was a falsified rail-delay experiment.
  Each is commented with an explanation — read it before touching.
- **Verify compiled artifacts, not just config edits.** Yocto silently drops
  kernel config options whose dependencies are unmet. Check the built `.config`
  and `strings` on the Image for the expected sentinels. This caught a near-miss
  where an fbcon image was accidentally built on top of the BIST flow and would
  have shown black.
- **Community layers are read-only** (`poky`, `meta-rockchip`, `meta-qt6`,
  `meta-rauc`). All changes go in `meta-hmi-platform` / `meta-hmi-app`.
- **Update `diary/SESSION-LOG.md`** as you go, and `diary/PROGRESS.md` /
  `diary/BLOCKERS.md` / `CLAUDE.md` §2 at milestones. Commit format:
  `[phase][component] what changed and why`.
